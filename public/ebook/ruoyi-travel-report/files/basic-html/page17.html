张钧益：建筑可阅读导览系统

                                         心得体会

      这次实训是我第一次真正意义上跟着老师完整地接触若依框架，并独立承担一个业务
模块的后端开发。以前做课程设计时，我习惯拿到需求就直接写代码，数据库表、接口、
前端页面往往是一边写一边改，最后能跑起来就算完成。但这次不一样，老师已经提供了
完整的前端小程序和网站页面，也给了明确的接口文档，我要做的不是“随便写一个能用
的后端”，而是让后端严格符合前端已经约定好的路径、参数和返回结构。刚开始我觉得
这只是个体力活，把 Controller 照着文档写一遍就行，但真正做下来才发现，后端开发
的难点从来都不只是“写出接口”，而是让接口在真实联调中稳定、准确、可维护地工作。

      在技术层面，我对若依框架的分层有了更具体的认识。Controller 层负责接收请求和
返回结果，Service 层处理业务逻辑和事务，Mapper 层负责数据库访问，实体类、DTO 和
VO 各自承担不同职责。以前我经常把这些东西混在一起写，Controller 里直接调 Mapper，
或者把数据库实体直接返回给前端。这次在 travel 模块里，我逐步理解了为什么要用
DTO 接收参数、用 VO 返回数据，为什么要用 @Transactional 保证主表和详情表要么一
起成功、要么一起回滚。尤其是景点模块的主表和详情表拆分，让我第一次直观感受到“高
频轻量字段”和“低频大字段”分开设计的意义：列表查询只查主表，详情页才去查富文
本，这样既减少了数据库压力，也让代码职责更清晰。

      实训过程中我也踩了不少坑，这些坑反而让我收获最大。比如有些表的主键没有设置
自增，我一开始以为前端会传 ID，后来才发现必须由后端统一用雪花 ID 生成，否则新增
数据会直接失败。再比如 startPage() 不能无脑加，后台列表需要分页，但小程序端不传
分页参数时应该返回全部数据，否则用户只能看到前十条。还有参数拼写问题，前端文档
里写的是 subClafficationId，而实体字段是 subClassificationId，如果不做兼容处理，
分类筛选就会静默失效。这些细节让我意识到，接口文档不是参考材料，而是前后端协作
的合同，任何字段名、参数位置、请求方法的偏差，都会在联调时变成实实在在的 bug。

      另一个让我印象深刻的点是代码健全性。以前我判断代码好坏的标准是“能不能跑”，
但这次我逐渐学会从更多维度去审视：主键策略是否统一，审计字段是否由后端填充，分
页是否兼容不同端，权限注解是否补齐，备份类是否还在被扫描，返回结构是否和文档一
致。这些内容在课堂上听起来很抽象，但在实际项目里，每一个小问题都可能让联调卡住
半天。尤其是在分析已有 Controller 和 Service 时，我发现有些方法虽然能编译通过，
但逻辑上并不完整，比如注释掉了 ID 生成、缺少事务、字段名和前端对不上。这让我明
白，能运行只是最低要求，健壮、规范、可维护才是工程代码的目标。

      通过这次实训，我也更清楚地认识到自己在软件工程方面的不足。第一是工程习惯还
不够好，写代码时容易只关注当前功能，忽略边界情况和异常处理；第二是对框架的理解
还停留在使用层面，遇到问题时排查速度不够快；第三是文档意识和接口契约意识需要加
